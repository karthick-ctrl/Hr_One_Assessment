# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72-74) | Returns HTTP 200 `{"status": "ok"}` statically without verifying that MongoDB is connected and responsive. Contract requires 200 only if MongoDB answers a ping, otherwise 503. | Stopping MongoDB or passing an unreachable `MONGO_URI` still yields 200 OK from `GET /health` instead of 503 Service Unavailable. | Added `client.admin.command('ping')` inside a try-except block; returns 200 on success and raises `HTTPException(status_code=503, detail="Database unavailable")` on failure. |
| 2 | `compute_late_minutes` (lines 33-37) | `minutes if minutes > 10 else 0` compares truncated integer minutes with 10. For a punch-in at 09:40:01 with shift start 09:30, elapsed seconds is 601, so `int(601 / 60) = 10`. Since `10 > 10` is false, it incorrectly returns 0 instead of 10. Rule R2 specifies late if strictly more than 10:00 after shift start, where 09:40:00 -> 0 and 09:40:01 -> 10. | Call `compute_late_minutes` with punch-in `09:40:01` on shift `09:30`. Expected 10, got 0. | Calculated total elapsed seconds between punch instant and shift start in IST; check `diff_seconds > 600` and return `int(diff_seconds // 60)` when true, else 0. |
| 3 | `compute_late_minutes` (lines 33-37) | Uses `punch_in.replace(hour=h, minute=m)`, which assumes `punch_in` is in local/naive time matching shift times, ignoring that MongoDB instants are UTC while shift times and calendar dates are IST (UTC+05:30). Furthermore, on overnight shifts (e.g. 22:00-06:00), punch-ins past midnight (e.g. 00:05 IST) belong to the shift that started the previous day (R1); replacing hour with 22 sets the start time in the future relative to the punch, resulting in negative minutes. | Punch-in at 00:05 IST for shift 22:00-06:00 returns 0 late minutes instead of 125 minutes. | Converted truncated punch instant to IST, identified attendance date and shift start datetime in IST (accounting for overnight shifts), and computed difference from that reference. |
| 4 | `compute_work_hours` (lines 40-41) | Uses Python's built-in `round((punch_out - punch_in).total_seconds() / 3600, 2)`. Python's `round()` uses round-half-to-even (banker's rounding) on floating-point numbers rather than the half-up rounding required by R4, leading to rounding discrepancies (e.g. 2.675 -> 2.67). | `compute_work_hours` on 9630 seconds (2.675 hours) yields 2.67 instead of 2.68. | Used `decimal.Decimal` with `ROUND_HALF_UP` on total elapsed seconds divided by 3600. |
| 5 | `compute_overtime` (lines 44-48) | Does not apply the 30-minute minimum threshold (R3). Any positive minutes between 1 and 29 are returned instead of 0. Also, for overnight shifts, shift end occurs on `attendance_date + 1 day`, but the function constructs `end` on `date_str`, causing overnight shift punch-outs to register ~1400+ minutes of overtime. | Punch-out at 18:45 on an 18:30 shift end returns 15 minutes overtime instead of 0. Punch-out at 06:40 on a 22:00-06:00 overnight shift returns 1480 minutes instead of 40. | Handled overnight shift calendar date roll-over (`date + 1 day`) for `shift_end`, calculated elapsed minutes since `shift_end`, and returned `minutes if minutes >= 30 else 0`. |
| 6 | `create_employee` (lines 78-85) | Concurrency race condition: uses check-then-insert (`find_one` then `insert_one`). Two concurrent create requests for the same `emp_code` can both pass `find_one` and create duplicate documents. Unique index was not created on startup. | Firing concurrent requests `POST /employees` with the same `emp_code` results in duplicate documents in MongoDB. | Created a unique index on `employees.emp_code` at app startup, wrapped `insert_one` to catch PyMongo `DuplicateKeyError`, and raised HTTP 409. |
| 7 | `create_employee` and `list_employees` (lines 82, 95) | Returns `created_at` as a Python `datetime` object (serialized to ISO 8601 string), violating the OpenAPI schema which requires `created_at` to be an integer count of epoch milliseconds (`EpochMillis`). | Schema validation error: response body has `"created_at": "2026-01-05T04:30:00"` instead of integer epoch milliseconds (e.g. `1767587400000`). | Converted `created_at` to integer epoch milliseconds (`int(dt.replace(tzinfo=timezone.utc).timestamp() * 1000)`) in outgoing employee representations. |
| 8 | `list_employees` (line 93) | Pagination offset calculation is off by one page: `skip = page * page_size`. For `page=1, page_size=20`, `skip = 20`, skipping the first page of results entirely. | `GET /employees?page=1&page_size=20` returns items 21-40 rather than items 1-20. | Changed formula to `skip = (page - 1) * page_size`. |
| 9 | `list_employees` (line 94) | `total` is calculated as `db.employees.count_documents({})`, which counts the entire collection without applying the `department` filter, violating R10 ("total always reflects the applied filters"). | Query `GET /employees?department=Sales` in a collection with 50 employees (10 in Sales) returns `total: 50` instead of `total: 10`. | Passed query filter `q` to `count_documents(q)`. |
| 10 | `list_employees` (line 95) | Missing sort clause. The contract requires employees to be sorted by `emp_code` ascending. Starter returns documents in arbitrary insertion order. | Response items are not sorted alphabetically by `emp_code`. | Added `.sort("emp_code", 1)` to the query. |
| 11 | `punch_in` (line 101) | Does not handle unknown employee: `emp = db.employees.find_one(...)` returns `None` if `emp_code` does not exist, causing `emp["shift_start"]` on line 113 to raise `TypeError`, resulting in an unhandled 500 Internal Server Error instead of 404. | Calling `POST /attendance/punch-in` with non-existent `emp_code: "EMP9999"` returns HTTP 500. | Added check `if not emp: raise HTTPException(404, "Employee not found")`. |
| 12 | `punch_in` (lines 102-103) | `ts = datetime.fromtimestamp(body.punched_at / 1000)` uses local system timezone instead of UTC, fails to truncate sub-second milliseconds to whole seconds (R1), and derives `date` as `ts.date().isoformat()` which fails for overnight shifts where a punch-in before `shift_end` belongs to the previous day (R1). | Punch-in at 05:30 IST for an overnight shift (22:00-06:00) assigns date to current day instead of previous day. Milliseconds are not truncated to whole seconds. | Truncated epoch ms to whole seconds (`(ms // 1000) * 1000`), converted to UTC datetime, converted to IST, and applied overnight shift date logic per R1. |
| 13 | `punch_in` (lines 104-118) | Concurrency race condition: check-then-insert (`find_one` then `insert_one`) allows concurrent punch-ins for the same employee and date to create duplicate records or conflict unhandled. | Concurrent `POST /attendance/punch-in` requests yield multiple records or 500s rather than exactly one 201 and the rest 409. | Created unique compound index on `attendance_logs(emp_code, date)` at startup, wrapped insertion to catch `DuplicateKeyError`, and returned HTTP 409. |
| 14 | `punch_in` and `list_attendance` (lines 119, 149) | Injects internal `id` (`str(res.inserted_id)`) into attendance response objects. The contract explicitly forbids `_id` and states attendance records have no ID (addressed by `(emp_code, date)`). | Schema validation failure: `AttendanceRecord` schema contains unexpected field `"id"`. | Removed `_id` and avoided adding `"id"` field. |
| 15 | `list_attendance` (lines 144-147) | In-memory loading and sorting: executes `docs = list(db.attendance_logs.find(q))` and sorts in Python using `docs.sort(...)`. This causes memory exhaustion and severe latency on collections of ~100k records. Additionally, it sorts only by `date` desc, omitting the required secondary sort by `emp_code` asc. | Query times out or causes high RAM usage on 100,000 records; records on the same date are not sorted by `emp_code` ascending. | Delegated sorting and pagination to MongoDB using index-backed `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`. |
| 16 | `list_attendance` (lines 127-142) | Missing date range validation. If `date_from > date_to`, the endpoint returns 200 with an empty list instead of HTTP 422 as specified in `openapi.yaml`. | `GET /attendance?date_from=2026-07-10&date_to=2026-07-01` returns 200 instead of 422. | Added validation `if date_from and date_to and date_from > date_to: raise HTTPException(422, "date_from cannot be greater than date_to")`. |
| 17 | `EmployeeIn` and `PunchInIn` models (lines 53-67) | Missing request body validation: `emp_code` lacks pattern `^EMP\d{4,6}$`, email lacks email format validation, `shift_start == shift_end` is not rejected, `PunchInIn.status` allows arbitrary strings (e.g. "ABSENT") instead of only `PresenceStatus` (`PRESENT`, `WFH`, `ON_DUTY`), and `punched_at` lacks bounds validation (`100000000000` to `4102444800000`). | Creating an employee with invalid code `"ABC"` or identical shifts `"09:30"` and `"09:30"` succeeds with 201 instead of 422. Punching in with `"status": "INVALID"` succeeds. | Added Pydantic field validators, regex patterns, and enums conforming strictly to OpenAPI schemas. |

Also note anything you looked at and decided was **not** a defect, and why:
- `load_dotenv()` without arguments at the top of `app/main.py`: `dotenv.load_dotenv()` defaults to `override=False`. This means environment variables already present in the execution environment (such as `MONGO_URI` and `MONGO_DB` injected by test harnesses) take precedence over values in a local `.env` file, adhering to the requirement that real environment variables must win.
